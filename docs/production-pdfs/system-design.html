System Design

SmartCode System Design Document

Production-oriented system design for the current SmartCode architecture, with current-state constraints and near-term scale recommendations.

1. System Objective

SmartCode is an online coding-practice platform that lets users sign up, log in, browse coding problems, run and submit solutions, track progress, compete in battle mode, and optionally receive AI coaching. The current implementation is optimized for fast launch and iterative product growth rather than heavy enterprise scale.

3. Major Functional Modules

High-value relationships

  • User to submissions
  • User to solved/favorite problems
  • Battle to challenger, opponent, winner, and problem
  • Study plan to problem list

5. Scalability and Reliability Design

Current strengths

  • Simple separation between frontend and backend
  • Managed infrastructure reduces ops burden
  • MongoDB Atlas is suitable for early growth
  • Independent frontend/backend deploys speed iteration

Current constraints

  • Render cold starts can affect first-request latency
  • No strong auth hardening yet
  • No automated regression tests
  • Observability is mostly dashboard-log based

Near-term improvements

  • Add password hashing and safer auth flows
  • Add backend health check and route smoke tests
  • Introduce structured logs with request identifiers
  • Cache heavy read paths if traffic grows

Scale-up path

  • Move to a more consistent always-on backend tier
  • Add rate limiting on auth and submission endpoints
  • Add monitoring and alerting for crashes and latency
  • Split judging from general API if submission traffic spikes

6. Security Design Priorities

  1. Hash passwords with bcrypt before wider public use.
  2. Rotate exposed MongoDB credentials and keep secrets only in Render/Vercel dashboards.
  3. Restrict CORS to exact trusted frontend domains.
  4. Add request validation on sensitive backend routes.
  5. Consider auth tokens or session management instead of trusting plain credential flow only.

7. Observability and Debug Strategy

Area Current tool Recommended next step
Frontend failures Browser console and Vercel deploy logs Add client error reporting
Backend failures Render logs Add structured logging and route-level diagnostics
Database health MongoDB Atlas metrics Track slow queries and usage growth weekly
AI dependency Backend fallback behavior Log coach provider mode for observability

8. Recommended Production Architecture Over the Next 30 Days

  • Keep the current Vercel + Render + Atlas architecture for now.
  • Stabilize auth and add tests before adding many new features.
  • Introduce a clear incident playbook and backup cadence.
  • Improve judging isolation if competitive coding usage grows meaningfully.
  • Document env vars and deploy steps in one team-owned source of truth.
